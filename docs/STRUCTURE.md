# 코드 구조

- `index.html`의 `<script>` 순서가 곧 의존성. `vs.html`은 같은 캔버스에 같은 스크립트 목록을 쓰므로 두 페이지의 목록을 같이 맞춘다. `core/timers.js`는 `battleEngine.js` 앞(파싱 시점 호출), `core/rng.js`도 `battleEngine.js` 앞, `views/battleLayout.js`·`fxSystem.js`·`bitmapFont.js`·`uiDraw.js`는 각 사용자 앞, `logic/seatControllers.js`와 `net/*.js`는 `battleEngine.js` 뒤(런타임에만 참조), `core/game.js`는 마지막.
- ESM 전환 불가 — 테스트가 `(0, eval)('Game')`로 스크립트 스코프 전역을 98곳에서 잡는다.
- `BattleEngine`의 상태 필드를 옮기지 말 것 — 테스트가 `e.p1`/`e.deck`/`e.currentState` 등을 199곳에서 직접 읽는다. 함수 이동은 안전.
- `autoPlay.js`의 `decideDiscard(hand, 0.7, null, ctx)` — `tests/measure/cpu-winrate`가 이 값을 중립 베이스라인으로 쓴다.
- `battleSequencer`가 `engine.scene.fx.list`를 직접 읽는다.
- 매니페스트(`assets.js` `toLoad`)에 없는 id로 `playSound`를 부르면 조용히 무음. 테스트 헬퍼 `getMissingSfx()`로 잡는다.
- `Assets.load`는 `window.onload` 뒤 `Game.init`에서 시작하므로, 페이지 `load` 이벤트를 늦추는 것은 모두 게임 자원 요청을 늦춘다. 그래서 역 계산기 iframe은 `data-src`만 두고 처음 열 때 `src`를 채운다(`game.js` 역 계산기 버튼, `battleMenuSystem.js` HELP 둘 다).
- 역 계산기 `yaku-calc.html`은 한 페이지가 두 모드다. `?live`(게임 iframe·모바일 새 창)는 원본 헬프 화면(`../sq/RULES.md` 4.4): 정렬 3종, 선택한 역의 조건·예시 패·부족한 장수를 줄이는 패, 손패에서 그 역에 쓰이는 패 들어 올리기. 예시 패는 표시되는 역명과 같은 변형을 따른다(`YakuDistance.exampleTiles(index, meta)`: 장기·필살기는 `meta.char`의 캐릭터 패와 그 색 무기패, 일색·초일색·순일색은 `meta.color`의 색). 파라미터 없이 열면 해설서에 있던 역 판정 테스터를 이은 단독 페이지(패를 직접 골라 판정). 판정은 `logic/yakuDistance.js`(원본 30개 함수의 부족 장수·사용 장수 포팅, 게임 판정 `yakuLogic.js`와는 별개)이고 이름·점수는 `BattleConfig.YAKU_NAMES`·`YakuLogic.SCORES`를 쓴다.
- 손패는 `QADebug.sync`가 `window.__haiyuki__`를 만들 때마다 `publishHand`로 iframe(`#yaku-frame`)과 새 창(`window.__yakuPopup`)에 `postMessage({type:'haiyuki-hand'})`로 밀어 준다(손패·오픈 세트·버림 수·상대 펑 수가 바뀔 때만). 양쪽 버림패와 상대 펑 세트는 종류별 남은 장수(9 − 보이는 장수, `YakuDistance.unseenCounts`)를 세는 데 쓰고, 남은 장수를 전부 더해도 못 만드는 역은 '완성 불가'로 표시한다(`reachable`). 도라는 종류만 정하고 패 산에서 빼지 않으므로 세지 않는다. `file://`에서는 iframe이 부모를 직접 못 읽어 이 경로가 필수이고, 같은 출처(http)에서는 패널이 `parent.__haiyuki__`를 직접 읽는 폴링도 겸한다. 패널은 열리면 `haiyuki-hand-request`를 보내 현재 손패를 받는다. 메시지에는 라운드 번호도 들어 있어 라운드가 바뀌면 패널이 선택 줄을 정렬 첫 줄로 되돌리고(같은 라운드에서는 유지), `Game.changeScene`이 전투가 아닌 장면으로 갈 때 `QADebug.clearPanel`로 빈 손패를 보내 패널을 비운다(`window.__haiyuki__`는 테스트가 읽으므로 건드리지 않는다). 전투 장면을 벗어나면(`Game.changeScene`) `QADebug.clearPanel`이 `window.__haiyuki__`를 지우고 빈 손패를 보낸다. 역 계산기는 같은 출처면 0.2초마다 `__haiyuki__`를 직접 읽기도 하므로, 메시지만 보내고 스냅숏을 남겨 두면 지난 손패가 다시 그려진다.
- BGM은 `Assets.bootBgm`(로딩 징글·타이틀)만 `canplaythrough`까지 기다리고, 나머지는 요소만 등록해 뒤에서 받는다. 덜 받은 BGM을 `playMusic`해도 버퍼가 차면 재생이 시작된다. 로딩·타이틀 장면이 새 BGM을 쓰게 되면 `bootBgm`에 넣는다. 반복 BGM은 요소의 `loop`에 더해 `ended`가 오면 그 요소가 지금 곡이고 `loop`가 켜져 있고 음소거·일시정지가 아닐 때만 처음부터 다시 튼다. 휴대폰에서 `loop`가 걸린 곡이 끝에서 멈추는 일이 있었다.
- 폰트는 KODDI 공식 배포 웹폰트(`KoddiUDOnGothic-Regular/Bold.woff2`)를 `docs/fonts/`에 그대로 두고 `haiyuki.css`의 `@font-face`로 쓴다. `index.html`은 공용 `atah.io/fonts.css`를 링크하지 않고 이 두 파일만 `preload`한다. `Game.init`은 폰트 로드(최대 3초)를 기다리므로 폰트 용량이 곧 시작 지연이다.
- URL 파라미터: `?mode=story`(=`watch`)는 스토리 온리 캐릭터 선택으로, `?mode=tutorial`은 튜토리얼로 로딩 직후 바로 간다(스플래시·타이틀 생략, `LoadingScene`). `?debug`는 디버그 패널, `?gamepad`는 가상 패드(토글 시 URL에 남긴다).
- 자원 한 개가 실패하면 `Assets.maxAttempts`(4)번까지 `retryDelayMs`씩 늘려 가며 다시 받는다. 끝내 실패하면 `Assets.failed`에 id를 모으고, `Assets.load(onComplete, onError)`는 `onComplete` 대신 `onError(failed)`만 부른다. `LoadingScene`은 이때 오류 문구를 그리고 타이틀로 가지 않으며, 아무 키나 누르면 새로 고친다. 지연 등록되는 BGM(`bootBgm` 밖)은 요소만 만들고 끝나므로 재시도 대상이 아니다.
- 역 판정(`yakuLogic.js`)은 손패를 13종류 개수 벡터(`countsOf`, `PaiData.TYPES` 순서)로 바꿔 `_evalCounts`에서 메모한다(키 = 13진수×2 + 오픈 여부, 상한 `MEMO_MAX`면 비움). 오픈 손패는 `CLOSED_ONLY` 역을 건너뛰므로 `checkYaku`·`checkTenpai`에 `open`(= `engine.isOpen(player)`)을 넘겨야 하고, 전체 손패는 `getFullHand`로 만든다. 패 색은 종류에 묶여 있다는 전제이고, 종류와 색이 어긋난 패가 들어오면 `countsOf`가 null을 돌려 `checkYaku`만 옛 경로(`analyzeHand`)로 간다. AI(`aiLogic.js`)의 수용 패·리치 점수 탐색은 배열 복사 없이 이 벡터를 증감하며 돈다 — 한 CPU 차례에 `checkYaku` 1.5만 회가 거의 전부 메모 적중으로 바뀌어 롱태스크가 사라졌다(`tests/perf/REPORT.md`).

## 자리와 컨트롤러

- 전투는 두 자리(자리 번호 0·1)로 돌고, 자리마다 컨트롤러(`engine.controllers.P1`·`.CPU`, `logic/seatControllers.js`)가 결정을 내린다. `engine.p1`은 항상 로컬, `engine.cpu`는 항상 상대이고, 자리 번호와의 대응은 `engine.localSeat`(기본 0, 온라인 게스트는 1)가 정한다: `whoAt(seat)`·`seatOf(who)`·`playerAt(seat)`. `engine.seats`는 자리 순서의 플레이어 배열. 기본은 P1 = `HumanController`(아무 것도 하지 않고 UI 입력을 기다림), CPU = `AIController`. `BattleEngine.init(data)`의 `data.controllers`·`data.localSeat`로 바꿔 끼운다. 온라인 설계는 `ONLINE.md`, 구현은 "온라인 대전".
- 엔진은 자리에 무관한 적용 함수만 가진다: `drawFor(who)`, `discardFor(who, index)`, `declareRiichi(who)`, `declareTsumo(who, auto)`, `declarePon(who, tile)`, `declareRon(who)`, `useSkill(id, who)`, `confirmTileExchange(who, indices, skillId?)`, `finishRoundSetup(who)`, `activateLastChance(who)`. 연출(표정 방향, 리치 배너 타임라인·곡, 뽑은 패를 잠깐 보여 주는 `CPU_DISCARD_HOLD`, 상대 캐릭터의 버림 대사)은 자리에 따라 값만 다르다. 옛 이름 `confirmDraw`·`playerDraw`·`discardTile`·`commitDiscard`·`executeAction`·`checkPlayerActions`·`checkCpuActions`·`checkActiveSkills`는 얇은 래퍼로 남아 씬·테스트·`autoPlay.js`가 쓴다.
- 컨트롤러가 답하는 지점(모두 "결정하라"는 통지이고, 답은 엔진 적용 함수를 불러 전달한다): `onDrawWindow(engine, who, { tile, canPon })` 상대가 버린 직후(펑 또는 뽑기. 론은 리치 중 화료패면 규칙상 자동이라 결정이 아니다), `onTurn(engine, who, { drew })` 뽑은 뒤 또는 펑·론 교환 뒤 차례, `onCounterPrompt(engine, who, skillId, resolve)` 상대 론에 초발도·론 교환을 쓸지, `onRoundSetup(engine, who, skillId)` 라운드 시작 패 교환(답은 `confirmTileExchange`), `onNagari(engine, who, resolve)` 라스트 찬스를 쓸지, `onDoraBomb(engine, who, resolve)` 리치 승리 때 도라 폭진을 쓸지(`engine.offerDoraBomb`가 승리 시퀀스의 결과 팝업 뒤에 묻는다. 자리에 무관하게 같은 위치), `autoStopRoulette(engine, who)` 룰렛을 키 없이 자동 정지할지와 그때의 정지 위치 `rouletteStopAt(engine, who)`(AI·자동 테스트의 사람은 `ai` 스트림으로 20~29, 네트워크는 메시지가 올 때까지 `Infinity`), `update(engine, who, dt)` 상대 차례 상태에서 매 틱, `poll(engine, who, dt)` 상태와 무관하게 매 틱(있을 때만, 네트워크 컨트롤러가 큐를 비우는 데 쓴다).
- 상대 자리 상태는 `STATE_CPU_TURN` 하나이고 `engine.cpuPhase`가 `'draw'`(뽑기 창: 펑·뽑기 대기)와 `'turn'`(버림·리치·쯔모·비기 대기)을 가른다. 로컬 자리는 `STATE_WAIT_FOR_DRAW`·`STATE_PLAYER_TURN`. `isDrawWindow(who)`·`isTurn(who)`가 두 자리를 같은 모양으로 묻는다. 생각 시간(`CPU_THINK_TIME`, 자동 테스트 3틱)은 `AIController.update`가 `engine.timer`로 재고, 엔진은 기다리기만 한다. 펑 뒤 차례는 `timer`를 `PON_THINK_CREDIT`(15)에서 시작해 생각 시간이 그만큼 짧다.
- 순서 의존 로직은 자리 번호 기준이다: 배패는 자리 1부터 3·3·3·2(시퀀서 `DEAL` 스텝의 `seat`), 라운드 시작 셋업 비기도 자리 1 → 0, 선공은 `firstSeat`(0 또는 1)를 뽑아 `firstTurn` 문자열로 바꾼다. 나가리의 라스트 찬스는 자리 0 → 1 순으로 묻고, 텐파이 여부도 자리 순서로 넘긴다.
- 한 차례에 능동 비기 하나 제한은 자리별 플래그 `player.skillsUsedThisTurn`이고 그 자리가 뽑을 때 풀린다(`engine.skillsUsedThisTurn`은 P1 플래그의 별칭). 상대 차례는 막지 않는다.
- 라운드 끝 판정(`turnCount > 20`, 덱 소진)은 버림 확정(`commitDiscardFor`)과 뽑기 직전에만 돈다. 틱 주기 검사는 두지 않는다 — 양쪽 엔진이 같은 논리 지점에서 끝나야 하기 때문이고, 덱은 20턴 안에 소진되지 않는다.
- 초발도로 버림패가 사라진 뒤에는 론을 건 쪽이 뽑기 창에 들어간다(사람이면 뽑기 버튼을 누른다).
- 상대 론에 대한 반격 비기 제안은 `SKILLS_ENABLED`가 켜져 있을 때만 양쪽에 뜬다.
- `showPopup`은 같은 종류의 팝업을 10틱 안에 두 번 띄우지 않는다(`totalTicks` 기준).
- 크리티컬·수경 보정은 `startWinSequence`에서 한 번만 곱한다. 우라도라는 표 도라와 같은 종류가 나올 수 있다.
- `SkillRegistry` 항목의 훅은 모두 선택이다: `canUse(engine, who, user)` 추가 조건, `execute(engine, who, user, opponent)` 효과, `aiScore(engine, ctx)` AI 욕구(점수 + 0~0.2 난수가 0.6을 넘으면 발동, `ctx = { who, isTenpai, isPlayerRiichi, turn, profile }`). 플래그 `multiUse`는 라운드·턴 제한 면제, `autoFlow`는 전용 흐름에서만 발동(`useSkill` 경로 차단). 반격 비기(`EXCHANGE_RON`·`SUPER_IAI`)와 `DORA_BOMB`은 항목 없이 `SkillFlows`가 엔진 흐름에서 직접 부른다.
- 시퀀서 스텝 `CALLBACK`은 콜백이 `engine.sequencing`을 통째로 바꾸지 않았을 때만 다음 스텝으로 넘어간다. 모르는 스텝 종류는 경고하고 건너뛴다.

## 난수

- 전투 안의 무작위는 `Math.random`을 쓰지 않고 `engine.rng`의 스트림만 쓴다. `core/rng.js`의 `Rng.create(seed)`가 32비트 시드에서 이름 붙은 스트림 셋을 독립적으로 만든다(마스터 시드와 스트림 이름을 섞어 시드, mulberry32). 스트림 API는 `random()`·`int(n)`·`pick(array)`·`shuffle(array)`(제자리).
- 시드는 `BattleEngine.init(data)`의 `data.seed`에서 오고, 없으면 `Rng.randomSeed()`(`Math.random`을 쓰는 유일한 곳)가 만든다. `engine.seed`에 남고, 스트림은 `init`에서 한 번 만들어 라운드가 바뀌어도(`startRound`) 이어 쓴다. `init`은 전투마다 한 번이다.
- 스트림 고르는 기준: 판에 영향을 주면 `deck`, 보이기만 하는 것이면 `fx`, AI의 판단이면 `ai`.
  - `deck`: 덱 셔플(`generateDeck`), 도라·우라도라, 선공 `firstSeat`, `drawTiles`의 `luck` 편향과 easy 드로우 어시스트, `exchangeTiles`가 덱에 되돌려 넣는 위치.
  - `fx`: 전투 배경(`init`), 버림 대사 발동 확률·`RANDOM` 몫(`rollDiscardDialogue`), `pickDialogue`의 대사 선택, 도라 룰렛 회전 수(`DORA_ROULETTE`). 소비는 자리에 무관하다("온라인 대전"의 `fx` 대칭 규칙).
  - 각 스트림은 `calls`에 `random()` 호출 횟수를 센다(상태 해시용).
  - `ai`: `AIDecisions.shouldReact`·`useActiveSkills`, `AILogic`의 softmax 버림·리치·펑 확률, `SkillFlows.pickRonExchangeTile`·라스트 찬스 자동 정지 위치·`executeCpuTileExchange`의 확률과 셔플. 온라인에는 AI가 없어 동기화 대상은 아니고, 시드만으로 오프라인 경기를 재현하려고 같은 체계에 둔다.
- `AILogic`은 엔진을 받지 않으므로 `init`이 `AILogic.rng = engine.rng.ai`로 꽂는다(엔진 없이 부르면 임의 시드 스트림이 지연 생성된다). `decideDiscard(hand, skill, profile, ctx)` 시그니처는 그대로다.
- 전투 밖(타이틀·크레딧·캐릭터 선택·컨티뉴 연출, 초상화 눈 깜빡임)은 `Math.random` 그대로다. 튜토리얼은 도라·배패가 레슨 데이터라 난수의 영향이 없다.
- 라운드 기록 `engine.roundHistory`는 `init`에서 비우고 `recordRound(entry)`(같은 라운드는 대체)로 쌓는다. 승리는 `BattleSequencer.startWinSequence`의 결과 값 계산 단계, 나가리는 `startNagariSequence`에서 쓴다. 비기 사용(도라 폭진·반격·라스트 찬스)은 `engine.roundNotes`에 라운드마다 모았다가 항목에 옮긴다. 항목 모양은 `ONLINE.md` 6절. 화면 스냅샷 `visual.spec.ts`의 `VS MODE 로비 화면`은 `vs.html?preview=` 상태별로 640·360 폭에서 찍는다.
- 행동 로그 `engine.actionLog`는 `init`에서 비우고 매치 내내 쌓인다(라운드마다 비우지 않음). 항목은 `{ round, who, type, ...payload }`, `who`는 `'P1'`/`'CPU'`. 버린 패는 손패 인덱스가 아니라 `{ type, color }`로 적는다. 종류: `draw`, `discard`(`tile`), `pon`(`tile`), `riichi`, `tsumo`(리치 중 뽑은 화료패로 엔진이 스스로 건 것은 `auto: true`), `ron`, `skill`(`skill` id. 반격 비기도 `useSkill`을 거치므로 여기 찍힌다), `exchange`(`tiles`, 교환 없이 확정하면 빈 배열), `react`(`use`, 상대 론에 반격 비기를 쓸지의 답), `nagari`(`use`, 라스트 찬스 확인의 답), `doraBomb`(`use`), `lastChance`(발동), `lastChanceStop`(`shown`, 룰렛이 멈춘 시점에 보인 장수). 기록은 적용 함수의 맨 앞, 상태가 바뀌기 전에 한다(온라인의 상태 해시가 이 시점을 기준으로 한다). `engine.onAction(entry)` 훅이 있으면 항목마다 부른다. 기록만 하고 재생은 없다. 같은 시드의 자동 테스트 경기는 로그가 같아야 한다.

## 온라인 대전

설계는 `ONLINE.md`. 같은 브라우저의 두 탭(`BroadcastChannel`) 또는 릴레이 서버(`relay/`, WebSocket)로 1:1 대전이 끝까지 돌고, 끝나면 같은 방에서 재대전한다.

- 파일: `net/transport.js`(`BroadcastChannelTransport(roomCode)`와 `WebSocketTransport(relayUrl, roomCode, role)`: `send(msg)`·`onMessage(cb)`·`onEvent(cb)`·`close()`. WebSocket 쪽은 JSON 문자열로 주고받고 릴레이의 `peer` 메시지를 `onEvent`의 `joined`·`left`·`full`로, 소켓 `close`·`error`를 `closed`로 올리며 `relay` 플래그가 참이다. 스스로 닫지 않았는데 소켓이 닫히면 콘솔에 닫힘 코드·이유와 마지막 수신·송신 뒤 지난 시간, 페이지가 보이는지를 남긴다(`QuickMatch`의 로비 소켓도 같다). 전송층 선택은 `OnlineMatch.makeTransport`(주소는 `OnlineMatch.relayUrl`): `?transport=local`이면 `BroadcastChannel`, 아니면 `?relay=` 또는 `BattleConfig.ONLINE.RELAY_URL`(`js/data/battleConfig.js`, 배포한 `*.workers.dev` 주소를 넣는 자리, 기본 빈 문자열)이 있으면 WebSocket. Playwright `online-local.spec`은 `transport=local`, `online-relay.spec`은 `wrangler dev`를 띄워 `?relay=ws://127.0.0.1:포트`), `net/onlineMatch.js`(`OnlineMatch.create({ host, code, char, seed })`가 만드는 매치 객체. 접속·핑·수신 큐 `inbox`·행동 전송·실패 처리·재대전. `OnlineMatch.current`가 진행 중인 매치. 상태가 바뀌면 `onChange`를 부른다), `net/netController.js`(`NetController`: 상대 자리 컨트롤러), `net/quickMatch.js`(`QuickMatch`: 릴레이 `/lobby` 소켓 하나. 페이지를 여는 동안 붙어 있어 `presence`를 받고, 끊기면 5초 뒤 다시 붙는다. `queue`·`unqueue`, 짝이 지어지면 `onMatch({code, role})`로 로비가 그 코드의 매치를 만든다. `?transport=local`이면 연결하지 않고 시작 화면에 퀵 매치 줄이 없다. `online-relay.spec`이 인원 표시·취소·짝짓기를 본다), `net/onlineLobby.js`(`OnlineLobby`: 패널 DOM 담당, `OnlineStageScene`: 패널 뒤에 까만 캔버스만 그리는 빈 장면).
- 자리: 호스트가 자리 0, 게스트가 자리 1(`engine.localSeat`). 양쪽 모두 `engine.p1`이 자기이고 `engine.cpu`가 상대라서 렌더러·씬·테스트는 그대로다. 순서 의존 로직(배패·셋업·선공·라스트 찬스 순서)은 자리 번호로 돌므로 두 엔진이 같은 판을 만든다.
- 접속: 양쪽이 `hello`를 0.5초마다 보내다가 상대의 `hello`를 받으면 멈추고 한 번 더 답한다(먼저 연 탭의 첫 메시지가 버려져도 만난다). 호스트의 `hello`에 시드와 비기 설정이 실린다. 연결 뒤에는 1초마다 `ping`을 보내고 10초 동안 아무 메시지도 없으면 끊김으로 본다(`BroadcastChannel`에는 끊김 신호가 없다). 릴레이 경로는 `hello`를 `peer joined` 뒤에 시작하고 `ping`·타임아웃을 쓰지 않으며, `peer left`는 `left`, `peer full`은 `full`, 소켓 끊김·접속 거부는 `disconnect`로 `fail`에 들어간다(대기 화면에서도 `OnlineLobby.onChange`가 처리).
- 진입: 온라인 대전(VS MODE)은 `vs.html`에서만 시작한다. `index.html` 머리의 인라인 스크립트가 `?mode=vs`를 `location.replace`로 `vs.html`(나머지 파라미터 유지)로 보낸다. 로딩이 끝나면 스플래시·타이틀 없이 `OnlineLobby.begin()`이 빈 장면으로 바꾸고 HTML 패널(`#online-panel`)을 보인다. 패널과 토스트는 `#game-container` 안의 `#online-layer`(캔버스를 덮고 `container-type: inline-size`)에 있어 `--ol-u`(컨테이너 폭/640)로 모바일에서 같이 줄어들고, 전체 화면에서는 레이어가 캔버스 크기에 맞춘다. 무대 배경은 `OnlineStageScene`이 `bg/STAFFBAK.png`로 그린다. `index.html`에도 같은 스크립트가 올라가지만 진입 경로가 없다. `body.online-page`가 온라인 페이지 표시이고 `OnlineLobby.isPage()`가 읽는다. 상단바는 소리·역 계산기·게임패드·전체 화면뿐이라 `game.js`의 난이도·비기 버튼 처리는 요소가 없으면 건너뛴다. `noindex`이고 `sitemap.xml`에 없다.
- 온라인 캐릭터 선택은 상대 커서에 `CPU` 대신 `RIVAL`이 적힌 `face/select_cursor_vs.png`(원본 `select_cursor.png`의 빨간 칸 글자판을 넓혀 다시 그린 것)를 쓴다. 숫자(P1·P2)는 화면마다 내가 1이 되어 양쪽이 어긋나므로 쓰지 않는다.
- 로비 상태: `OnlineLobby.view`가 `start` → `wait` → 접속되면 `hidden`으로 패널을 닫고 캐릭터 선택(`CharacterSelectScene` `mode: 'ONLINE'`)으로 간다. 매치가 끝나면 `BattleScene.exitOnline`이 `OnlineLobby.returnFromMatch`를 불러 `ended`를 보인다. 그리는 쪽은 `OnlineLobby.stateOf()`가 매치에서 만든 상태 객체(`view`·`code`·`role`·`result`·`rounds`·`canRematch`·`rematch`)를 `render(state)`가 `#online-panel`의 마크업으로 바꾸는 것뿐이고(상태가 같으면 다시 그리지 않아 입력값이 유지된다. `show`는 항상 다시 그린다), 클릭은 패널에서 위임으로 받는다. `VS MODE`·`WIN`·`LOSE`는 `glyphs()`가 `ui/alphabet.png` 스프라이트 칸(`GLYPH` 표: `I`는 폭 24·시작 4)으로 만든다. `copyText`는 `navigator.clipboard`를 쓰고, 없거나 실패하면 숨은 textarea 선택 + `execCommand('copy')`로 폴백한 뒤 성공하면 토스트. 실패(`match.failed`: `disconnect`·`desync`)는 어느 단계에서든 매치를 닫고 메시지와 함께 `start`로 돌아간다. 캐릭터 선택에서 ESC·`취소`·`나가기`는 방을 나가 `start`로 간다. 코드 입력은 `OnlineMatch.normalizeCode`로 I·O를 뺀 대문자 다섯 글자만 받는다(입력 상자에 포커스가 있는 동안 `Input`은 키를 무시한다). `?room=코드`로 열면 입력 없이 바로 `joinRoom`. `?preview=이름`은 `previewStates()`의 가짜 상태를 `render`해 보이고 버튼은 막는다. 스타일은 `haiyuki.css`의 VS MODE 절(`--ol-*` 토큰).
- 캐릭터 선택: 각자 고르고 `pick`을 교환하며, 상대 초상화는 상대의 `pick`이 오면 뜬다. 같은 캐릭터 허용, 눈썹개는 자기 쪽에서 해금됐을 때만 고를 수 있다(오프라인과 같은 필터). 상대가 눈썹개를 고르면 해금 여부와 무관하게 실루엣·`???` 표기 없이 일반 캐릭터처럼 그린다: `BattleScene.cpuMasked`와 `BattleRenderer.maskedCpuName`이 온라인(`engine.online`)에서는 꺼진다. 둘 다 고르면 조우 씬 없이 `BattleScene`으로 간다(`{ online: match, playerIndex, cpuIndex }`).
- 재대전: 매치가 끝나면 `match.ended`. `다시 대전`은 `requestRematch`로 `rematch`를 보내고 `rematchMine`을 세운다(상대 대기 문구 표시). 호스트는 양쪽 `rematch`가 모이면 `Rng.randomSeed()`로 새 시드를 뽑아 `rematchStart {seed}`를 보내고 `beginNext`, 게스트는 `rematchStart`를 받으면 `beginNext`. `beginNext`는 시드를 바꾸고 캐릭터 선택 값·요약·수신 큐·검사 횟수를 비운 뒤 `onChange`로 로비가 캐릭터 선택부터 다시 시작시킨다. 방과 핑은 그대로 이어진다.
- 나가기: `match.close()`가 `bye`를 보내고(탭을 닫을 때도 `pagehide`에서 닫는다) 받은 쪽은 10초를 기다리지 않고 바로 처리한다. 실패 사유는 `left`(`bye`, `상대가 나갔습니다`)·`disconnect`(응답 없음, `연결이 끊어졌습니다`)·`desync`(`동기가 어긋났습니다`)이고, 알림은 `OnlineLobby.status(text)`가 `#online-status`(`vs.html`의 `#online-layer` 안, 게임 창과 같은 프레임 상자 토스트)에 띄운다. 전투 밖의 사유는 로비 시작 화면으로 돌아가며 알린다.
- 제한 시간: `BattleConfig.ONLINE`(초 단위, `ticks(sec)`로 환산). `seatControllers.js`의 `OnlineClock`이 상태에서 시계 단계(`phase`: 뽑기 창·내 차례·교환·룰렛·결과·상대 확인 대기)를 계산하고, `HumanController.update`(`updateLogic`이 온라인일 때 P1 컨트롤러에 매 틱 부름)가 `engine.clock`을 갱신해 다 되면 `OnlineClock.expire`가 기본 행동을 한다. 단계가 바뀌면 시계를 새로 시작하고, 뽑기 창·결과 창은 입력 지연(`DRAW_INPUT_DELAY`·`RESULT_INPUT_DELAY`) 뒤부터 센다. 상대 자리 시계는 같은 계산으로 표시만 한다(상대 확인창은 `NetController`의 대기 중 `resolve` 유무로 판단). 확인창은 `HumanController.confirm`이 `showConfirm`에 `limit`을 넘겨 `BattleScene.updateConfirm`이 `onNo`를 부른다. 숫자는 `BattleRenderer.drawClock`. 그림 숫자(`BattleRenderer.drawNumber`, `ui/number.png`·`ui/number_gold.png`)는 글자 간격이 16px로 고르지 않아 `BattleConfig.INFO.numbers.sx`의 글자별 시작 x에서 14px씩 자른다. 리치 자동 진행·`isAutoTest`·튜토리얼에서는 시계가 없다.
- 결과 창 공동 진행: `confirmResult(who)`는 온라인에서 결과 창 상태일 때만 동작하며 `confirm {win: resultSeq}` 행동을 남기고 `resultSeq`를 올린다. 받는 쪽 `NetController`는 `win`이 현재 `resultSeq`와 같고 결과 창 상태일 때만 적용하고, 작으면 `poll`이 큐에서 버린다(해시 비교 전). `confirm`은 상태를 바꾸지 않으므로 해시는 그대로 비교한다.
- CPU 인계: 전투 중(`BattleEngine.online === match`, 매치가 안 끝남) `Match.fail`은 매치를 무효로 하지 않고 `takeOver(reason)`을 부른다. `takenOver`를 세워 핑·수신·전송(`onAction`)을 멈추고 `inbox`를 비운 뒤 `BattleEngine.handOverToAI('CPU')`가 컨트롤러를 `AIController`로 바꾼다. `NetController.release`가 대기 중이던 반격·라스트 찬스·도라 폭진을 AI 판단으로 풀고, 상대 교환 대기·룰렛 정지 위치·상대 뽑기 창도 AI가 이어받는다. `OnlineLobby`는 `onChange`에서 `상대가 나가서 CPU가 이어받습니다`를 띄우고, 매치 끝 패널에서 `다시 대전`을 숨긴다(`requestRematch`도 막음). 요약에 `takenOver`가 남는다.
- 전투 설정: 시드·`localSeat`는 매치에서, 컨트롤러는 P1 `HumanController`·CPU `NetController`, 난이도 `normal`(드로우 어시스트 0, `luck`은 캐릭터 특성이라 그대로), 비기는 `OnlineLobby.begin`이 `SKILLS_ENABLED = true`로 고정한다. 토너·세이브·컨티뉴·엔딩은 관여하지 않는다. 자동 테스트의 도라 룰렛 생략은 온라인에서는 하지 않는다(`fx` 소비가 양쪽에서 같아야 한다).
- 메시지 = 행동 로그 항목. `engine.onAction` 훅으로 `who === 'P1'`인 항목을 그대로 보내되 `ron`은 받는 쪽이 무시하고, 자동 쯔모(`auto`)·반격 비기의 `skill` 항목·`lastChance` 발동은 보내지 않는다(양쪽 엔진이 스스로 한다). 받은 메시지는 `inbox`에 쌓이고 `NetController.poll`이 머리부터 적용 조건을 보아 적용한다. 조건이 안 맞으면 기다리고(연출 중일 수 있다), 폴링된 3600틱이 지나도록 적용되지 않으면 `desync`.

  | 메시지 | 적용 조건 | 적용 |
  |---|---|---|
  | `draw` | `isDrawWindow('CPU')` | `drawFor('CPU')` |
  | `pon {tile}` | `isDrawWindow('CPU')`이고 마지막 버림패를 펑할 수 있음 | `declarePon('CPU', 마지막 버림패)` |
  | `discard {tile}` | `isTurn('CPU')` | `cpu.hand`에서 패 식별로 인덱스를 찾아 `discardFor` |
  | `riichi` | `isTurn('CPU')`, `canDeclareRiichi` | `declareRiichi('CPU')` |
  | `tsumo` | `isTurn('CPU')` | `declareTsumo('CPU')` |
  | `skill {skill}` | `isTurn('CPU')` | `useSkill(id, 'CPU')`(거부되면 `desync`) |
  | `exchange {tiles}` | `setupWaiting === 'CPU'` | 패 식별들을 인덱스로 바꿔 `confirmTileExchange('CPU', …)` |
  | `react {use}` | 미해결 `onCounterPrompt` | 보관한 `resolve(use)` |
  | `nagari {use}` | 미해결 `onNagari` | 보관한 `resolve(use)` |
  | `doraBomb {use}` | 미해결 `onDoraBomb` | 보관한 `resolve(use)` |
  | `confirm {win}` | `msg.win === engine.resultSeq`이고 결과 창 상태 | `confirmResult('CPU')`. `win`이 `resultSeq`보다 작으면(이미 지난 결과 창) 적용 없이 버림 |
  | `lastChanceStop {shown}` | `engine.lastChance`가 `CPU` 자리이고 `spin` 단계 | `lastChanceSetStop`: `stopAt = shown`, 이미 지나쳤으면 `shown`으로 되감음 |
  | `ron` | 항상 | 무시(콘솔 로그만) |

- 상태 해시 `engine.stateHash()`: 자리 0·1 순으로 손패(패 키 정렬)·오픈 세트·HP·MP, 버림 목록, 덱 길이, 라운드, `turnCount`, `rng.deck.calls`·`rng.fx.calls`를 이어 붙여 FNV-1a 32비트. 보내는 쪽은 행동을 기록하는 순간(= 적용 함수 맨 앞, 상태 변경 전)의 해시를 메시지에 싣고, 받는 쪽은 적용 직전에 자기 해시와 비교한다. 다르면 `desync`로 매치를 멈추고 로비 패널에 알린다(끊김은 `disconnect`). 매치 결과·행동 로그·검사 횟수는 `match.summary`에 남는다.
- `fx` 대칭 규칙: `fx` 스트림 소비는 자리와 무관한 논리 지점에서만 일어나고 보여 주기만 가른다. 버림 대사(`rollDiscardDialogue`)는 어느 자리가 버리든 같은 조건으로 확률을 굴리고 대사를 고르되 말풍선은 버린 자리가 `CPU`일 때만(`triggerDialogue`의 `silent` 옵션, 뽑은 패는 `lastDrawInfo[who]`와 종류(type·color) 비교 — 손패 위치는 양쪽 엔진이 같지 않다). 펑 대답(`PON_REPLY`)은 `declarePon`이 시작될 때 `pickDialogue`로 고르고 대답하는 쪽이 `CPU`일 때만 띄운다(시퀀스 안에서 고르면 메시지 적용 시점에 따라 소비 순서가 갈린다). 비기를 쓰는 대사도 쓰는 순간 고른다(`useSkill`). 맹호일발권·기합 리치를 버릴 때 말하는 두 번째 대사는 사람 자리와 온라인 상대 자리만 말하고 오프라인 CPU는 말하지 않는다(시퀀스 안에서 고르며 소비는 양쪽이 같다). 라운드 시작 패 교환 대사는 `confirmTileExchange`가 양쪽 자리에서 고르고 P1이면 띄우지 않는다. 도라 폭진은 양쪽이 같은 위치(결과 팝업 뒤)에서 컨트롤러에 묻는다. 배경·도라 룰렛 회전 수·리치·비기·승패 대사는 원래 자리에 무관하다.
- URL: `vs.html?room=<코드>`는 초대 링크(바로 참가). `&char=<CharacterData 인덱스>`는 캐릭터 선택 생략(첫 매치만), 호스트는 `&seed=<32비트>`로 첫 시드를 고정한다(테스트·수동 확인용).
- 로그: 온라인 로그는 모두 `[Online]` 태그의 `console.log`이고 `OnlineLog`(`net/onlineMatch.js`)가 모은다. 항상 남기는 것: 접속 시작(`connect`: 전송층·릴레이 주소·방 코드·자리), 릴레이 이벤트(`relay event joined|left|full|closed`), 성립(`connected`: 시드와 `hello` 수신·송신 횟수)과 `pick`(양쪽 캐릭터), 제한 시간 자동 행동(`timeout auto …`, `OnlineClock.expire`), 재대전(`rematch requested|accepted|start`), 결과 창 `confirm sent|received`, 실패·인계(`console.error`, 사유 `disconnect`·`left`·`full`·`desync`). `desync` 오류 객체의 `detail`은 `Match.describeState`가 만든 내 쪽 상태로 `stateHash`가 보는 항목(자리 순서의 손패·오픈 세트·HP·MP, 버림, 덱 길이, 라운드, `turn`, `rng.deck`·`rng.fx` 호출 수)에 `state`·어긋난 메시지(`msg`: `type`·`seq`)·마지막으로 적용한 메시지 10개(`applied`)를 더한 것이다. `vs.html?debug=net`일 때만 보내는 메시지(`>> type seq=N rX tY`)와 받은 메시지(`<<`), 적용 시점(`applied … queued=N ticks`: 큐에서 기다린 틱), 60틱마다 기다리는 중(`.. waiting for type … state=`)을 더 남긴다(`ping`은 제외). 릴레이 쪽 로그는 `relay/README.md`.
- 수동 확인: 한 브라우저에서 `vs.html`을 탭 둘로 열어 한쪽 `방 만들기`, 다른 쪽에 링크로 접속. 같은 출처(같은 `http://` 서버)여야 `BroadcastChannel`이 통하고, `docs/`를 서버로 띄워야 효과음이 돈다. 한 탭을 닫으면 다른 탭이 바로 끊김 문구를 보인다.
- 테스트 `tests/online-local.spec.ts`: 한 브라우저 컨텍스트에 페이지 둘을 열고(호스트는 `방 만들기`로 코드를 읽고, 게스트는 `?room=`으로 접속) 양쪽 `Game.isAutoTest`·`Game.symmetric`을 켜 P1을 AI가 움직이게 한다(대칭 모드라 확인창 없이 반격·라스트 찬스·도라 폭진까지 AI가 답한다). 비기는 항상 켜지므로 끈 매치는 테스트가 `OnlineLobby.ready` 뒤에 `SKILLS_ENABLED`를 직접 끈다. 비기 on/off 각각 한 매치를 끝까지 돌려 `summary.failed`가 없고 해시 검사가 있었고 두 탭의 `actionLog`가 자리만 바꿔 같고 승자·HP가 대칭임을 단언한다. 라스트 찬스는 AI끼리 거의 안 나와서 배패 단계에 양쪽 `turnCount`를 18로 올리고 `cpuWantsLastChance`를 항상 참으로 바꾼 매치를 하나 더 돌린다. 사람 입력 경로는 호스트 탭을 자동 테스트 없이 두고 키로 뽑고 버린 패가 게스트의 상대 버림으로 나타나는지 본다. 로비 DOM 흐름(방 만들기 → 코드 표시 → `코드 복사`·`바로 입장 링크 복사` 토스트와 클립보드 내용 → 링크로 접속 → 패널 닫힘, 코드 입력 정규화), `index.html?mode=vs`가 `vs.html`로 가는지, 재대전(`WIN`/`LOSE`가 양쪽 반대, 목록 줄 수가 `summary.rounds`와 같고 승/패가 반대 → 양쪽 `다시 대전` → 새 시드로 두 번째 매치가 끝까지 동기), 나가기(상대 탭에 `상대가 나갔습니다`)도 본다. 동기 비교는 `confirm` 항목을 빼고 한다(양쪽이 동시에 눌러 한쪽 것이 버려질 수 있음). 결과 창 공동 진행은 한쪽만 넘기는 드라이버로 상대가 스스로 넘기지 않고 따라오는지, 제한 시간은 `BattleConfig.ONLINE` 값을 줄인 호스트로 자동 뽑기·맨 오른쪽 패 버림·결과 창 자동 `confirm`과 확인창 자동 거절을, CPU 인계는 상대 `close()`(`bye`)와 `fail('desync')`로 인계 뒤 끝까지 진행하고 `다시 대전`이 숨는지를, 상태 토스트는 입장·캐릭터 선택 대기·재대전 요청·이탈 문구를, 대기 제한은 `WAIT_SEC`·`WAIT_WARN_SEC`를 줄인 호스트가 경고 토스트 뒤 시작 화면으로 돌아가는지를 본다.

## CPU 스킬

- 지옥쌓기·수경·크리티컬·회복·버린 패 방어는 리치 중에 쓸 수 없다(`canUse`의 `!user.isRiichi`, 원본 `sq/RULES.md` 6.2). 사람은 리치 뒤 메뉴가 막혀 원래도 못 썼고, 이 조건으로 CPU도 같아진다. 라스트 찬스는 발동 때 `audio/barrier`(원본 SFX 12)를 낸다.
- 라스트 찬스(페톰 B)는 원본 `sq/FX.md` 4.11을 따른다(`SkillFlows.activateLastChance`·`updateRoulette`, 상태 `engine.lastChance`): 말풍선(20틱 뒤 키로 넘김, 최대 140틱) → 발동(MP 소모, `audio/barrier`, CPU는 손패 전부 공개 + `audio/discard`) → 10틱 → 쓰는 쪽 손패의 뽑은 패 칸에 남은 패산을 뽑는 순서(덱 끝)부터 4틱마다 한 장씩 보여 준다. 화료패가 없어도 돈다. 사람은 확인키·클릭을 누른 틱에 멈추고, 자동 정지(`autoStopRoulette`)면 컨트롤러의 `rouletteStopAt`(AI·대칭·자동 테스트의 사람은 20~29장)에서 멈춘다. 결과는 보인 장수 `shown`만으로 정해진다(`lastChanceSeek`가 `shown`에서 덱 위치를 되구한다). 멈춘 패가 그대로 결과이고 실제 뽑기 위치는 움직이지 않는다. 역이 되면 바로 쯔모 승리, 아니면 최대 200틱(키로 넘김) 뒤 나가리로 이어진다. 룰렛 중 효과음·강조는 없다. 나가리 때 사람 → CPU 순으로 판단하고, CPU는 원본 6.4의 조건(대기 최고 점수 ≥ 5000이고 그 종류가 보이는 수 < 6, `cpuWantsLastChance`)이면 쓴다.
- 비기의 MP는 "쓸 수 있는 하한 = 소모량"(`SkillData.cost`)이다. 원본은 린샹 도라 폭진(하한 12·소모 32)과 페톰 크리티컬(하한 32·소모 24) 두 칸만 두 표가 어긋나는데, 데이터 실수로 보고 따르지 않는다(사용자 결정, `sq/RULES.md` 6.2).
- CPU의 라운드 시작 패 교환(스마슈 `EXCHANGE_TILE`·눈썹개 `PAINT_TILE`)은 원본 규칙(`sq/RULES.md` 6.4·6.5)을 따른다. `SkillFlows.pickCpuTileExchange`가 손패를 무작위 순서로 훑으며 현재 MP 전부를 예산으로 장당 비용(6/4)씩 빼고, 보존 종류(스마슈: 린샹·화린·스마슈·유리, 눈썹개: 눈썹개 4종)가 아닌 패를 고르고, `executeCpuTileExchange`가 그 인덱스를 `confirmTileExchange`로 넘긴다(사람의 확정과 같은 경로: 기록·MP·교환·셋업 종료). 장수 상한은 없다. 스마슈는 사용 여부도 칸마다 독립 70%로 굴린다. 교환한 패를 덱에 되넣는 순서는 손패 순서가 아니라 패 종류 순이라 손패 정렬이 달라도 덱이 같다.
- 캐릭터 필드 `skillOffset`(기본 0)은 `BattleEngine`이 `cpuSkill`(0..1 클램프)에 더한다 — 버림패 실수와 스킬 발동 확률에만 걸린다(린샹 +0.05, 스마슈 −0.15, 화린 −0.10, 유리 +0.10, 페톰 +0.15, 나머지 0). 보통(쉬움도 같은 밴드)에서 어느 상대와 붙어도 매치 승률이 비슷해지도록 맞춘 값이다. 어려움은 실력 1.0 고정이라 보정이 올라갈 자리가 없어서 보정을 0으로 끈다 — 어려움은 모든 CPU가 최선을 다하는 상태이고 캐릭터 간 체급 차이가 그대로 드러나는 것이 의도다. CPU 난이도 보정이라 대칭 모드(실력 고정 1.0)에서도 0으로 둔다.
- `aiProfile.luck`은 캐릭터 특성이다: `drawTiles`가 뽑는 쪽(`who`)의 캐릭터 luck(`BattleEngine.luckOf`)만큼 덱 상단 몇 장 중 유리한 패(음수면 불리한 패)를 올린다. 사람 P1·CPU 어느 쪽이 그 캐릭터를 잡든 같고, 튜토리얼에서만 `luckEnabled`로 끈다. easy 드로우 어시스트는 별개의 P1 전용 난이도 기능.
- 눈썹개 버림패 AI(`AILogic.scoreDiscards`, `charId === 'mayu'`, 닫힌 12장 평가 한정)는 눈썹개 4종을 눈썹개 역에 필요한 장수(빨·노·파 4장, 보라 3장)까지는 버리지 않도록 `MAYU_KEEP_W`만큼 감점한다. 텐파이 단계 점수(`TENPAI_TIER`)보다 작아 텐파이는 깨지 않는다.
- CPU 스마슈의 `EXCHANGE_RON`은 `SkillFlows.pickRonExchangeTile`이 원본(`sq/RULES.md` 6.3)처럼 되가져온 패를 뺀 손패에서 종류 수 1인 칸 → 2인 칸 → 3 초과 칸 → 아무 칸 순으로 하나를 무작위로 골라 다음 차례에 버린다(되가져온 패는 `player.exchangeReturned`에 남고 AI 컨트롤러가 자기 차례에 고른다, 그 차례는 리치·AI 버림 판단을 건너뜀). 안전패 평가는 쓰지 않으므로 다시 론당할 수 있다.
- 대칭 모드(`Game.symmetric` + `Game.isAutoTest`, 엔진 `symmetric`)는 PvP 밸런스 측정용이다: P1도 CPU와 같은 AI가 움직인다. `AutoPlay.performSymmetricTurn`(비기 `checkActiveSkills('P1')`·쯔모·리치 `declareRiichi` 뒤 `shouldRiichi`·`decideDiscard`), 대기 중 펑(`tryP1AiPon`), 라운드 시작 교환(`executeCpuTileExchange(engine, id, 'P1')`), 론 반응(`AIDecisions.shouldReact`, 론 교환 뒤 `p1.exchangeDiscard`), 승리 때 도라 폭진(`onDoraBomb` 항상 예), 나가리 라스트 찬스(양쪽, 룰렛 자동 정지)를 CPU 쪽과 같은 규칙으로 쓴다. 자동 테스트의 P1 리치는 `declareRiichi('P1')`을 거쳐 로그에 남는다(온라인 테스트가 이 경로로 상대에게 알린다). 양쪽 실력 `SYMMETRIC_SKILL`(1.0), `skillOffset` 0, 드로우 어시스트 0(`luck`은 캐릭터 특성이라 그대로 걸린다). `aiProfile`(펑·방어 성향)은 캐릭터 것을 그대로 쓴다. 사람이 조작하는 P1 경로와 일반 CPU 대전 동작은 바뀌지 않는다.

## 튜토리얼

- 타이틀 `TUTORIAL` → `BattleScene`을 `{ tutorial: true, lessonIndex }`로 연다(플레이어·상대는 눈썹개를 뺀 무작위 서로 다른 캐릭터). 엔진은 `BattleEngine.tutorial`(null이면 본편)이 있을 때만 갈라진다. 레슨 데이터·나레이션은 `data/tutorialData.js`.
- 레슨 `plan`(플레이어 뽑기·버림·펑·론과 단계별 텐파이/역)이 단일 출처다: 뽑기 순서, 버릴 수 있는 패(버림 횟수째 한 종류), 검증 spec이 모두 여기서 나온다. `cpuDraws`는 CPU 뽑기 = 버림 순서.
- 판 준비: `startRound`가 `tutorialBuildDeck`으로 배패 순서를 덱 끝에 깔고 도라·우라도라를 레슨 값으로 고정. `drawTiles`는 큐에서 꺼내고 비면 덱에서 뽑는다. easy 어시스트 0, `luckEnabled` false, `BattleConfig.RULES.SKILLS_ENABLED`는 시작 때 끄고 `BattleScene.exitTutorial`이 복구. 툴바 비기 버튼은 `Game.syncSkillsButton`이 전투 시작·튜토리얼 종료·페이지 로드 때 켜짐/꺼짐 표시를 실제 값에 맞추고, 튜토리얼 중에는 `disabled`로 흐리게 둔다.
- 리치 선언은 `needRiichi` 레슨에서만 뜬다(`checkSelfActions`가 다른 레슨에서 RIICHI를 걸러 냄).
- CPU: 뽑은 패를 그대로 버리고 쯔모·리치·펑·론·비기 없음(`AIController`가 `engine.tutorial`이면 펑 창을 무시하고 차례에 마지막 패만 버린다), `triggerDialogue` 전부 무시.
- 버림 제한: `discardTile`이 `tutorialCanDiscard`로 거르고(틀리면 `audio/wrong`), 렌더러가 같은 함수로 못 버리는 패를 어둡게 칠한다. 리치를 걸어야 하는 차례(`tutorialWantsAction`)에는 리치 전까지 모든 패를 막는다. `needPon` 레슨에서 펑 가능 때 패를 가져오면 `tutorialFail` → 실패 나레이션 뒤 그 레슨 처음부터.
- 나레이션: 레슨 `script`의 `{ on, say }`를 순서대로 소비한다(엔진이 `tutorialEvent(이름)`을 부르고, 현재 가리키는 항목의 `on`과 같을 때만 발동. 항목에 `discards: n`이 있으면 플레이어가 n번째 패를 버린 뒤에만). 이벤트: `wait`·`drawn`·`discarded`·`tsumoChance`·`ponChance`·`afterPon`·`riichi`·`ron`·`win`(결과 창이 펼쳐진 뒤, `NARRATION.resultDelay`틱)·`afterResult`. 대사 안의 `\n`은 줄바꿈, `{…}`로 감싼 부분은 `NARRATION.highlight`(노란색)로 그린다. 떠 있는 동안 `engine.narration`이 `updateLogic`과 `BattleScene` 입력을 막고 확인키·클릭으로 넘긴다. 쯔모·론이 자동으로 나가는 지점(리치 중)은 `tutorialEvent`의 `onDone`으로 나레이션 뒤에 실행한다. `say`의 한 장은 문자열이거나 `{ text, look }`이고(`engine.narrationPage()`가 둘을 같은 모양으로 돌려준다), `look`은 `dora`·`uraDora`·`lastDiscard`·`actionButton`·`drawn`(방금 가져온 손패 맨 오른쪽 패)·`hand:<패 id>` 중 하나 또는 배열이다. 렌더러가 그 프레임에 그린 위치를 `_lookRects`에 모아 두고 `lookRects(state)`로 대상 사각형을 찾아 나레이션 위에 대상 가운데를 끝으로 하는 초록 화살표(원본 마우스 커서 `ui/mouse2.png` 그대로, 5프레임 순환, `NARRATION.look`)를 그린다. 대상이 `RESULT` 창과 겹치면 그 장 동안 `drawResult`를 건너뛴다. 대상의 중심이 화면 버튼(`날 수 있어!` 등) 안에 들면 그 장 동안 버튼도 그리지 않고(`actionButton`을 가리키는 장은 제외), 나레이션이 떠 있는 동안에는 손패를 어둡게 칠하지 않는다.
- 라운드 라벨은 `ui/lesson.png`(`INFO.labels.lessonPath`)로 바꾸고 숫자는 레슨 번호(`startRound`가 `currentRound`를 맞춤).
- 라운드 끝: `DAMAGE_ANIMATION`에서 HP는 본편처럼 깎되(레슨 1~4 합계로 상대 HP가 마지막 론에서 0이 됨) `matchOver` 대신 `tutorialNext`(다음 레슨 판 / 마지막이면 타이틀). `matchOver`·저장·컨티뉴 횟수는 건드리지 않는다. 전투 메뉴는 아가리·펑·리치·역 계산기·타이틀로만 둔다.
- 테스트: `tests/tutorial.spec.ts`(회귀 스위트 포함) — 레슨 데이터 판정 단언 + 타이틀에서 레슨 1~4 끝까지 + 펑 넘김 재시작 + 메뉴 타이틀로.

## 턴 진행 타이밍

- 원본 `usamain.sq`를 fxtrace로 실행해 센 틱에 맞춘다(`SPEED`): 사람 버림 → CPU 뽑기 21, CPU 뽑기 → 버림 22, CPU 버림 → 사람 뽑기 입력 가능 22(`DRAW_INPUT_DELAY`, 키·마우스 모두), 리치 중 사람은 CPU 버림 22틱 뒤 자동으로 뽑고(`RIICHI_AUTO_DRAW`) 50틱 뒤 자동 버림(원본은 자동 없음 — 웹 선택).
- 라운드 시작은 원본(`sq/FX.md` 4.10) 순서다: 도라 룰렛(2틱마다 종류가 하나씩 넘어가며 `audio/dora_roulette`, 26~51회 무작위) → 10틱 → 손패 칸 비움 효과음 → 5틱 → 배패를 CPU 먼저 3·3·3·2장씩 번갈아 8단계, 단계 간 5틱, 단계마다 `audio/discard`. 사람 패는 배패 중 앞면으로 놓이고(`isFaceDown` false), 다 놓인 뒤 30틱에 전부 엎고(`FACE_DOWN`) 15틱 뒤 정렬하며 공개(`FLIP_HAND`). 원본은 패가 이동하지 않고 그 틱에 자리에 나타나므로 웹도 이동 연출은 없다. 튜토리얼과 자동 테스트는 룰렛을 건너뛴다(도라 고정·측정 속도).
- 선공은 라운드마다 50% 무작위다(`RULES.RANDOM_FIRST_TURN`, `engine.firstTurn`, 원본 E10의 `rand(100) < 50`). 튜토리얼은 항상 사람 선공. `turnCount`는 "양쪽이 한 번씩 버린 사이클" 번호라서 후공 쪽이 버린 뒤에 올린다: 후공이 버린 직후 상대의 뽑기 창을 열고(`commitDiscardFor` → `openDrawWindow`), 그 창이 그 자리에서 바로 론·펑으로 닫히지 않았을 때만 올린다(AI의 펑은 즉시 결정되므로 턴을 올리지 않고, 사람의 펑은 창이 열린 뒤에 일어나므로 이미 올라가 있다). 그래서 어느 쪽이 선공이든 각자 20턴에 40장 버림으로 나가리가 된다. 후공의 첫 턴 쯔모 800은 `calculateBonuses`가 버림 수로 판단하므로 그대로 적용된다(버림 수 1의 론 400 분기는 후공이 리치일 수 없어 도달 불가). 테스트 헬퍼 `startBattle`은 기본으로 사람 선공 고정(`randomFirst: true`로 풀 수 있음).
- 승패 소리는 원본 `sq/FX.md` 4.12 순서다. 론·쯔모(라스트 찬스 성공 포함)는 `startWinSequence`가 이긴 쪽 손패 공개(CPU가 이겼을 때만 CPU 패를 엎은 채에서 공개) + `audio/discard` → 말풍선 20틱 + 최대 30틱(`DIALOGUE_REPLY`, 키로 넘김, 원본 120틱) → 승리 곡(사람 승 `audio/jingle_p1_win` = 원본 BGM 8, CPU 승 `audio/jingle_cpu_win` = BGM 9, `RESULT.TYPES.WIN/LOSE.jingle`)과 론·쯔모 배너를 같은 틱에 띄운다. 결과 창에는 징글이 없다. 도라 폭진을 쓰면 말풍선 20틱 + 최대 30틱(키로 넘김) 뒤에 바뀐 우라도라를 공개하고 결과 창이 뜬다(`offerDoraBomb`의 완료 콜백이 `REVEAL_URA` 앞에 `WAIT`·`WAIT_KEY`를 끼운다). 피해는 `audio/damage`(원본 SFX 13), 나가리 조각 두 개가 착지할 때마다 `audio/nagari_land`(SFX 9, 타임라인 `shakes` 틱에 `POPUP.TYPES.NAGARI.shakeSound`). 화린이 버린 패 방어 중일 때 버리는 소리는 `audio/flip`(SFX 15, `AUDIO.DISCARD_GUARDED`).
- 리치 선언 순서는 원본대로 "대사(20틱) → 상대 대답(원본 120틱, 웹 `DIALOGUE_REPLY` 30틱, 확인키·클릭으로 넘김) → 배너(82틱) → 버림". 사람은 리치 버튼 뒤 버릴 패를 고른 순간 이 시퀀스가 돌고 배너가 끝나야 패가 놓인다(`discardFor` → `startRiichiSequence` → `commitDiscardFor`). 상대 자리는 같은 시퀀스 앞에 21틱(`CPU_RIICHI_THINK`) 대기가 붙고 배너 타임라인이 `riichi_r`, 곡이 `bgm_tension`이다. 시퀀서 스텝 `DIALOGUE`·`WAIT_KEY`가 이를 맡고, 키로 넘기면 `BattleDialogue.hideAll`로 말풍선을 닫는다. 튜토리얼은 대사 없이 배너만. BGM은 시퀀스 끝의 `MUSIC` 스텝이 배너 뒤에 바꾸며, `updateBattleMusic`은 `declaringRiichi` 중인 쪽을 아직 리치가 아닌 것으로 본다(버튼을 누른 순간 먼저 바뀌지 않게). 리치봉은 원본처럼 `isRiichi`가 켜지는 순간(선언 버튼·비기 사용)부터 보이고, 색은 그때 `riichiStick`(0 흰색·1 금색·2 파란색)으로 정한다. `declareRiichi`는 0, `declareRiichiLock`은 비기가 넘긴 값(맹호일발권 1, 기합 리치 2)을 쓴다. 자리·그림은 `BattleConfig.RIICHI_STICK`. 리치 패를 버리기 전에는 메뉴의 리치 항목을 다시 골라 선언을 거둘 수 있다(`canCancelRiichi`·`cancelRiichi`, 온라인 행동 `riichiCancel`). 그동안 메뉴는 리치 항목만 켜 두고, 비기 리치(`riichiStick` 1·2)와 튜토리얼은 거둘 수 없다. 비기는 쓸 때 MP를 먼저 깎기 때문이다. 비기로 거는 리치(`declareRiichiLock`: 맹호일발권·기합 리치, 손패를 고정해 텐파이를 깨지 못하게 함)도 원본처럼 버리는 순간 같은 시퀀스를 탄다(원본은 두 비기가 '이번 버림에서 리치 선언' 플래그를 직접 켜고 버림 루틴이 그 플래그로 선언 연출에 들어간다, `sq/RULES.md` 비기 표). AI 판단 리치(`declareRiichi`)와 비기 리치 모두 같은 시퀀스를 탄다. `declareRiichi`는 `riichiSilent`를 끈다. 론 패 교환으로 되가져온 리치패를 다시 버릴 때만 `riichiSilent`로 시퀀스를 건너뛰고 버림패에 리치 표시만 한다.

- 전투 대사 흐름(원본 `sq/RULES.md` 3.11, `sq/FX.md` 4.7). 키 대기는 `WAIT_KEY`(확인키·클릭, 자동 테스트는 즉시)이고 길이는 `SPEED.DIALOGUE_REPLY` 30틱이다.
  - 버림(`rollDiscardDialogue`): 발동 `CHANCE.DISCARD` 50%(원본 21%) 중 `CHANCE.RANDOM` 10%는 `RANDOM`(칸 10)이고 리치 중이어도 나온다. 나머지는 버리는 쪽이 리치가 아닐 때만. 상대가 리치가 아니면 뽑은 패와 같은 종류를 버릴 때 `BAD_DRAW`(칸 7), 아니면 `GOOD_DRAW`(칸 6), 펑 직후처럼 뽑은 패가 없으면 `GOOD_DRAW`. 상대가 리치면 상대 버림에 없는 종류는 `DISCARD_UNSEEN`(칸 8), 리치 패를 포함해 리치 뒤 버림(양쪽)에 있는 종류는 `DISCARD_PASSED`(칸 9), 리치 전 버림에만 있으면 없음. 손패 평가·`turnCount` 제한·턴당 한 번 제한은 없고 버림 대사 뒤 멈춤도 없다.
  - 펑(`declarePon`): 펑한 쪽 대사 → 20틱 → 상대 대답 → 키 대기 → `PON` 배너 → `ACTION_WAIT` → 적용. CPU 펑도 같다.
  - 비기(`useSkill`): 대사 → 20틱 → 키 대기 → 효과(비기 팝업·소리·`processSkillEffect`). MP와 사용 표시는 즉시 반영하고 효과만 미룬다. 대사가 없으면(튜토리얼) 즉시. 끝나면 쓰기 전 상태로 돌아가므로 다음 행동 메시지는 그때까지 기다린다. 오프라인 CPU는 `useActiveSkills`가 참을 돌려주면 `AIController.run`이 시퀀스가 끝난 뒤 다시 `act`를 부르고, 사람 자동 플레이도 같다(`skillCheckDone`으로 한 턴에 한 번만 판단). 론 반격 비기(초 거합베기·론 패 교환)는 `useSkill`의 `onDone`으로 반격 처리를 대사 뒤로 미룬다. 도라 폭진은 대사 뒤 20틱 + 키 대기를 우라도라 공개 앞에 끼운다. 패 교환 비기(스마슈 A·마유 A)는 원본도 대사가 없다.
  - 맹호일발권·기합 리치: 예약(비기 사용)에서 한 번, 버릴 때(`startRiichiSequence`, `riichiStick` 1·2)에서 비기 대사를 한 번 더 말한다(대답 없음, 20틱 + 키 대기, 이어서 리치 배너). 오프라인 CPU는 원본(E16에서 한 번)대로 사용할 때만 말한다.

## 페이지 스타일

- 색은 gensei-pc98 `docs/style.css`의 `:root` 토큰을 그대로 복사해 쓴다(역할과 쓰임은 gensei-pc98 `docs/NOTES.md` "색상 토큰"). 그쪽 토큰이 바뀌면 같이 바꾼다. 예외: 역 계산기 iframe 칸(`yaku-calc.html`과 같은 원본 헬프 화면의 녹색 바탕 `#005c50`)과 가상 게임패드(유리 재질 자체 값). `yaku-calc.html`의 색은 원본 `graph/jp/helpbg`·`help`에서 가져온 자체 토큰(녹색 바탕, 남색 패널, 연보라 입체 버튼)이고, 패널 틀은 게임 창과 같은 `ui/frame/` 조각(모서리 4개·선 4개)을 CSS 배경 레이어로 깐 것이며 글자는 게임과 같은 KoddiUD 폰트다.
- 푸터 레이아웃·글자 크기는 공유 `https://atah.io/footer.css`, 색·그라디언트 윗선·여백은 gensei-pc98 `#footer`와 같게 `#main-wrapper #footer`(아이디 둘)로 덮는다. 공유 `footer.css`의 `opacity: 0.8`은 1로 되돌린다. 모바일에선 저작권과 버전을 한 줄로 둔다 — 에뮬레이터 크레딧이 없어 둘째 줄에 버전만 남기 때문.
- 글자 크기는 gensei-pc98 토큰(`--font-lg`·`--font-md`·`--font-sm`·`--font-xs`)을 따른다. 상단 레이블만 예외로, 옆의 버튼 이미지 높이(데스크톱 35px·모바일 27px)에 맞춘 px 값 `--toolbar-label`(18px·모바일 12px)을 쓴다. 다른 글자를 "레이블과 같게" 맞출 때는 이 값이 아니라 토큰을 쓴다. 푸터 위 링크 줄(`#site-links`)은 `--font-md`.
- `theme-color`는 `--bg`와 같은 값이라 모바일 브라우저 상단이 페이지 바탕과 이어진다.
- GA4 이벤트는 `dataLayer.push({ event, game: 'haiyuki' })`(사이트 공통 GTM)로 보낸다. `js/core/analytics.js`의 `Analytics.track`·`playStart`가 맡고 자동 테스트(`Game.isAutoTest`)에서는 보내지 않는다. `play_start`는 타이틀에서 BATTLE·TUTORIAL·STORY ONLY를 고를 때, `?mode=` 직행 때, VS 매치가 캐릭터 선택을 마치고 전투로 들어갈 때(재대전 포함) 보내고, 첫 `play_start`가 `PlayTime.start()`로 `play_milestone`(`minutes`) 집계를 켠다. `js/core/play-time.js`는 gensei-pc98 `emulator/play-time.js`를 그대로 복사한 공유 파일이다. 그 밖에 `tutorial_complete`(레슨 4까지 마침), `ending_reached`(`EndingScene` 진입), `gamepad_activate`(가상 게임패드 켬).

## 가상 게임패드·상단바

- `core/gamepad.js`와 `haiyuki.css`의 게임패드 부분은 gensei-pc98·suiko-web-v2 것을 바탕으로 한다(모양·토글 버튼·`gamepad_activate` 이벤트). 바꿀 땐 그쪽과 함께 맞춘다.
- 패유기만 다른 점: 확인 버튼은 `KeyZ`를 보낸다(Enter를 보내도 `input.js`가 Z로 정규화해서 동작은 같다). 마우스로도 눌린다(`battle-keys.spec`이 `page.click`으로 누른다). 켜짐 표시는 `body.gamepad-on`. 패드는 캔버스 위에 뜨지 않고 `padding-bottom: 180px`로 자리를 비운다.
- D-pad 버튼의 `padding: 6px 14px` — 에뮬레이터 페이지는 전역 `button` 패딩을 상속해서 아이콘이 그 크기로 보인다. 패유기엔 전역 규칙이 없어 D-pad에만 같은 값을 준다.
- `.btn-touch-only` 숨김은 `.toolbar-icon-btn.btn-touch-only`로 쓴다. `.toolbar-icon-btn`이 뒤에서 `display: flex`를 줘서, 같은 명시도면 숨김이 진다.
- `vs.html`의 상단바는 난이도·비기 그룹이 없고(역 계산기 그룹만 가운데) 나머지는 같다.
- `#toolbar-row`는 3열 그리드(왼쪽 음소거, 가운데 게임 옵션, 오른쪽 게임패드·전체 화면)이고 폭을 캔버스 640px에 맞춰 양끝 아이콘이 캔버스 가장자리와 맞는다.

## 일시정지

- 탭이 숨겨지면(`document.hidden`, 모바일 앱 전환 포함) 로딩 장면을 뺀 모든 장면에서 `Game.pause()`로 멈춘다: 로직 틱·효과음·BGM 정지, 입력 초기화. 돌아와도 자동 재개하지 않고 캔버스에 일시정지 아이콘(높이 48px, kaisin `src/input.ts`의 `ICONS.pause` 모양)만 띄운 채 Z/Space/탭·클릭으로 재개하며, 재개 첫 프레임 dt는 0이다. 로딩 중에는 멈추지 않는다. 자동 테스트는 제외.
- `blur`는 쓰지 않는다: 역 계산기 iframe을 누르거나 다른 창을 보며 둘 때도 포커스가 빠져 데스크톱에서 과하게 멈춘다. 모바일 앱 전환은 `hidden`이 함께 온다.

## 테스트 (`tests/`)

- 회귀 스위트 = `rules`(룰북 불변식·시나리오·멀티 라운드·쉬움 드로우 어시스트) `yaku` `bonus` `skills` `story` `battle-keys` `menu-keys` `battle-mouse` `visual` `tutorial` `pause` `replay` `online-local` `online-relay`. `online-*`는 "온라인 대전"의 테스트 방법.
- `replay.spec.ts`는 시드·캐릭터·난이도·비기 조합 30판을 자동 대전으로 끝까지 돌려 `actionLog` 전체·라운드별 `stateHash`·최종 결과를 `tests/golden/<이름>.json`과 비교한다. 다르면 처음 달라진 `actionLog` 항목이나 라운드를 메시지에 보여 준다. 의도한 동작 변경이면 `UPDATE_GOLDEN=1 npx playwright test replay.spec.ts`로 저장본을 다시 쓴 뒤 diff를 확인해 커밋한다. 갱신할 때 판마다 `신규`·`변경 없음`·첫 차이 지점과 달라진 항목 수가 한 줄씩 찍힌다. `startBattle`의 `seed`가 다르면 덱과 판이 달라지는지도 같은 파일에서 본다. 틱 수는 실행마다 달라 비교하지 않는다.
- 측정 도구는 회귀 스위트 밖에 둔다: `measure/`(CPU 승률, 전용 설정 `measure.config.ts`)와 `perf/`. 회귀용 설정은 `measure/`·`perf/`를 건너뛴다.
- `startBattle` 헬퍼는 기본으로 `SKILLS_ENABLED = false`로 전투를 시작한다(회귀 스펙 전제). 승률·행동 측정은 스킬이 켜져야 하므로 `measure/cpu-winrate`는 `skills: true`로 시작한다.
- CPU 승률·행동 지문 측정은 `measure/cpu-winrate.spec.ts`를 전용 설정 `measure.config.ts`로 돌린다(`npx playwright test --config measure.config.ts`, 서버 포트 `PORT` 기본 12802 — 회귀용 12801·사용자용 12800과 겹치지 않고 기존 서버를 재사용하지 않는다). 결과는 매치마다 `fingerprint-state.<커밋>.skills<0|1>.<난이도>.json`에 누적되고 같은 조건이면 이어받으므로 `MPC`(캐릭터당 추가 경기 수, 기본 10)로 짧게 끊어 여러 번 돌린다. `CHARS`로 캐릭터 지정, `SKILLS=0`·`DIFF=`로 조건 변경, `RESET=1`로 초기화. `fingerprint-results.json`은 누적 상태에서 매번 다시 만든다. 메인 체크아웃을 쓰지 말고 측정 워크트리(`../haiyuki-measure`, 브랜치 `measure`)에 `tests/`를 복사해 돌린다 — 측정 중 소스가 바뀌면 결과가 섞인다.
- `measure/cpu-winrate`는 매치(KO) 단위로 CPU 승률을 집계한다(경기별 승자·라운드 수, 95% 구간). P1은 CPU와 다른 6명을 순환하고(`P1_FIXED=1`이면 아타호 고정), 난이도 보통의 토너 진행도(`defeatedOpponents` 길이)를 0~4로 돌린다. P1의 확인창(도라 폭진·라스트 찬스)은 "예", 라운드 시작 패 교환은 교환 없이 확정, 룰렛은 자동 정지로 넘긴다. 속도를 위해 페이지 안에서 `Game.update`를 `TURBO`(기본 40)번씩 직접 돌리며, 샤드를 나누지 말고 한 프로세스로 돌리는 편이 빠르다(700경기 약 13분).
- `visual.spec.ts`는 `maxDiffPixels: 0`(0.001 비율로는 215px 변화를 놓친 적 있음). 베이스라인은 `visual.spec.ts-snapshots/`에 커밋한다. 전투 배경 `engine.bgPath`는 랜덤이라 고정 필수.
- `retries: 1` — 재시도 통과는 `flaky`로 표시된다. 간헐 실패는 소스를 stash해도 재현되므로 두 번 연속 실패만 진짜.
- 키/마우스는 down → 70ms → up으로 눌러야 프레임에 잡힌다.
